# BA Analysis — DocumentUploadModal + DocumentsPage Render Tests (TD-13)

## Business Rules

1. `DocumentUploadModal.handleSubmit`'s `familyMemberId || null` conversion means the native `<select>`'s empty-string default ("Nicht zugewiesen") must translate to `null` in the `onSave` call, not the empty string — identical pattern to `FamilyMemberFormModal`'s absence of this exact issue (that component takes `color`, not an optional relation) but directly analogous to `useDocuments.uploadDocument`'s own `familyMemberId ? formData.append(...) : (nothing)` guard tested in TD-12.
2. `DocumentUploadModal`'s submit guard is `disabled={!file || uploading}` — no file selected blocks submission entirely, same "defense in depth" shape as `FamilyMemberFormModal`'s name/initials guard (TD-06), though here there's only one required field (no independent `handleSubmit`-level re-check of `file` beyond the `if (!file) return` early return — worth confirming that early return specifically, not just the disabled button).
3. `DocumentsPage.handleExtract` clears **both** `extractionError` and `successMessage` at the start of every new extraction attempt (`setExtractionError(null); setSuccessMessage(null)`), before the `extractEvents` call even resolves — so a fresh extraction attempt on a *different* document immediately clears a leftover banner from a *previous* document's attempt, even before the new attempt's own outcome is known.
4. `extractingId` (not a boolean) tracks *which* document is mid-extraction — only the `DocumentItem` whose `doc.id === extractingId` receives `extracting={true}`; every other rendered `DocumentItem` (including ones for other documents) must show `extracting={false}` during another document's in-flight extraction. This is a real multi-item edge case a single-document test fixture can't exercise.
5. `handleExtractionDone(createdCount)` is a pure string-formatting decision independent of `extractEvents`/`extractingId`/`extractionError` — it fires only from `ExtractEventsModal`'s own `onDone` prop, called after the review-and-confirm flow inside that modal (already tested there), not from `handleExtract` itself. `DocumentsPage`'s own test only needs to prove it's wired to that callback correctly, not re-derive when `ExtractEventsModal` decides to call it.
6. `error` (from `useDocuments`) and `extractionError` (page-local state) are two **independently rendered** banners (`{error && ...}` then `{extractionError && ...}`, both `className={styles.errorBanner}`) — both can theoretically be visible simultaneously (e.g. a load failure and a subsequent extraction failure), they are not mutually exclusive or reset by one another.

## Edge Cases

1. **Family member `<select>` left at "Nicht zugewiesen"** — `uploadDocument`'s `familyMemberId` argument must be `null`, not `''`, per Business Rule 1.
2. **Extraction on one document while a different document is also extractable and visible** — only the triggering `DocumentItem` shows the loading/spinner state (`extracting` prop scoped to `extractingId === doc.id`), per Business Rule 4. Requires a fixture with 2+ extractable documents.
3. **A second extraction attempt after a first one failed** — the stale `extractionError` from attempt 1 must be cleared the instant attempt 2 starts (before attempt 2's own result is known), not just replaced once attempt 2 resolves — per Business Rule 3. Same for a stale `successMessage` being cleared by a fresh attempt.
4. **`handleExtractionDone` with `createdCount === 0`** — the singular/plural boundary is specifically at `1`, not `<= 1`; `0` must produce the plural form `"0 Termine wurden angelegt."`, not the singular. Easy off-by-one to regress (e.g. `createdCount <= 1 ? singular : plural` would incorrectly pluralize-fail at 0).
5. **Documents grouped across multiple family members plus an unassigned group simultaneously** — a fixture with at least 2 different assigned members + 1 unassigned document, confirming `DocumentGroupHeader` renders once per group in the right order ("Allgemein" first) and each group's `<DocumentItem>`s are scoped to the correct group (not all documents dumped under every header).
6. **`loading` true with `documents` already non-empty from a previous successful load** (e.g. a manual refetch scenario) — per the component's actual JSX (`{loading && <p>Lädt…</p>}` is unconditional on `documents.length`, and the group/list rendering block is gated on `documents.length > 0` with no `!loading` condition) — worth confirming: does the list stay visently rendered under the "Lädt…" text, or does `loading` alone not hide it? **Investigated directly in the component**: `{loading && ...}` and `{documents.length > 0 && ...}` are two independent sibling blocks with no mutual exclusion — if `loading` is `true` AND `documents.length > 0` simultaneously, **both** the "Lädt…" text and the full document list would render at once. This is almost certainly only reachable via a refetch-while-populated scenario that doesn't currently exist in this hook's usage (initial `loading` starts `true` with `documents` empty), so a dedicated test isn't required by any AC — flagging as a documented characterization possibility for Architect, not a required test.
7. **Empty state's exact gating (`!loading && documents.length === 0 && !error`)** — must NOT show if either `loading` or `error` is true, even with zero documents — e.g. an error-during-initial-load state (loading became false, error is set, documents is still `[]`) must show the error banner, not the empty state.

## Data Model Implications
None — this story adds test coverage only, no production code changes, no new types/fields.

## Open Questions

1. **NON-BLOCKING** — `story.md`'s Notes flags whether `ExtractEventsModal` should be mocked for `DocumentsPage`'s tests, given reaching its `onDone` callback through a fully-real render would substantially duplicate that component's own already-existing 20-test suite. Recommend **mocking `ExtractEventsModal` at the module level** for `DocumentsPage.test.tsx` specifically (via `vi.mock('../components/ExtractEventsModal/ExtractEventsModal', ...)`, rendering a minimal stand-in that exposes its received props for assertion and lets a test directly invoke the `onDone`/`onClose` callbacks it was given) — this is the standard "test the integration boundary, not the already-tested internals" pattern, and keeps `DocumentsPage.test.tsx` focused on what TD-13 actually asks for (the wiring, not `ExtractEventsModal`'s own UI). `DocumentUploadModal` and `DocumentPreviewModal`, by contrast, don't need mocking — `DocumentUploadModal` gets its own full test file per this same story (AC1), and `DocumentPreviewModal`'s involvement in `DocumentsPage` is a single trivial prop-pass-through with no multi-step flow to short-circuit.
